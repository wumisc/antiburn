## 二、保命通知：进程被杀后自己回来

之前的痛点是「服务被 HyperOS 回收 → 通知消失 → 用户压根不知道防烧屏已经停了」。现在是三层：

1. **45 秒快速补刀**：`onDestroy` / `onTaskRemoved` 里排一次 45 秒后的自愈闹钟（只在「不是用户主动停止」时排）；
2. **15 分钟兜底巡检**：`setAndAllowWhileIdle` 的**不精确**闹钟，覆盖「没来得及排闹钟就被 LMK 强杀」那条路径。不申请 `SCHEDULE_EXACT_ALARM`（不给你多一个授权项），不拿 wake lock，醒来只读一个进程内布尔值；
3. **通知上「立即恢复」按钮**：万一系统拒绝后台启动，你手点一下就行。

**系统真的拦了怎么办**：`startForegroundService` 抛异常不崩、不重试风暴，只记一行 `HEAL block=<异常类型> manual=`，同时**弹一条可点的兜底通知**「防烧屏守护已停止 · 点此恢复」——点通知属于用户交互，再拉服务就不再受限。

**不做流氓软件**：你点通知上的「停止」后置 `stoppedByUser`，之后不再自愈、不再补闹钟；下次手动打开才恢复。

服务活着时通知标题会如实写「已自愈恢复 · 时:分」，不假装一直没停。

## 三、「本应用隐身」打开后自己关：真凶与修法

**因果链**（api102 分支专属）：

1. `AppVisibilityStore` 用 `new ComponentName(app, getPackageName() + ".LauncherAlias")` 拼组件名；
2. 清单里的 `.LauncherAlias` 是按**命名空间**展开的 → 真实组件是 `io.github.wumisc.antiburn.LauncherAlias`（aapt2 实测）；
3. 但分支的 `getPackageName()` 是 `io.github.wumisc.antiburn.api102` → 拼出 `…api102.LauncherAlias`，**包里不存在**；
4. `setComponentEnabledSetting` 直接抛 `IllegalArgumentException` → 点击回调崩 → 应用关闭；
5. 原代码用 `apply()` 异步落盘，进程一崩偏好就丢，重开时开关又显示「正常显示」——看起来就是「打开后自动关闭」。

**修法**（四条一起上，不只堵这一个点）：

1. `launcherAlias()` 改为从 `getPackageInfo(GET_ACTIVITIES | MATCH_DISABLED_COMPONENTS)` 里找 `endsWith(".LauncherAlias")` 的真实组件，找不到才退回拼接；
2. `applyLauncherVisibility` 全程 try/catch，切换后**再读一次**组件状态做校验，返回 boolean；
3. 偏好改 `commit()` 同步落盘，失败时回写旧值，磁盘与界面永远一致；
4. UI 判返回值：失败时两个开关一起退回、弹「桌面入口切换失败，请重试或重启桌面」，不再显示假的「已隐藏」。

**说明**：合并后的 3.2.25 因为 applicationId == 命名空间，本来就不会触发这条；修复是为了「渠道改包名 / 双开 / 以后改 applicationId」都不再踩同一个坑。

## 五、已知限制

- `POST_NOTIFICATIONS` 被你拒掉时，兜底通知不可见（自愈仍然会执行，只是没提示）；

## 六、JVM 沙盒（Robolectric）：隐身与自愈在假 Android 里真跑了一遍

云电脑没有 `/dev/kvm`、2 核 / 3.7 GB，起不了 Android 模拟器，更装不了 Magisk + Zygisk + LSPosed，所以改走 JVM 沙盒：

- 依赖：`testImplementation 'org.robolectric:robolectric:4.16'` + `junit:4.13.2`，`testOptions.unitTests.includeAndroidResources = true`；
- 一个坑：compileSdk 37（Android 17）的 android.jar 删了 `android.hardware.fingerprint.FingerprintManager`，而 Robolectric 的 `ShadowApplication` / `ShadowNotificationManager` 还引用它 → test 编译报 `cannot access FingerprintManager`。解法是把 `platforms/android-36/android.jar` 只挂到 test 编译期（`testCompileOnly`），运行期 Robolectric 用的是 android-all jar，不影响主工程；
- 测试类：`app/src/test/java/io/github/wumisc/antiburn/SandboxSafetyTest.java`，`@Config(sdk = 36, application = Application.class)`——刻意不用 `AbApplication`，否则 onCreate 会去拉 ConfStore、清日志线程、su 杀进程，全是无关重活。

**17 个用例，全绿**

| 用例 | 验证到的事实 |
|---|---|
| launcherAliasIsDeclaredInManifest | `…LauncherAlias` 在清单里真存在（不是拍脑袋拼的组件） |
| applyLauncherVisibilityReallyTogglesComponent | 真实切到 DISABLED、再切回 ENABLED，全程无异常 |
| togglePersistsAndReadsBack | `commit()` 落盘，同进程立刻读回一致 |

## 九、源码体检：又抓到 3 个真 bug（已修 + 已加守卫）

这一轮按「兼容性 / 全量 / 源码」三个角度扫了一遍，落地的三个都不是纸上问题：

**① 「停止守护」是一条永远走不到的死代码**（最严重的一条）

`GuardService.onStartCommand` 里有完整的 `ACTION_STOP` 分支：置 `stoppedByUser`、`markUserStop`（落盘 + 注销闹钟）、`stopSelf`。但全工程**没有任何地方构造过这条 PendingIntent**，通知上的动作只有「立即恢复」——也就是说「用户点了停止就永不复活」这套逻辑用户根本触发不到，除了强行停止没有别的退出方式。我上一轮说「你点停止就记账」是错的，先纠正。

修法：`HealReceiver.stopPending()`（requestCode 1004）→ `GuardService` 的通知挂第二个动作「停止守护」。点了之后：注销两档闹钟、写「别回来」档位、`stopSelf`；之后自动巡检在 `onReceive` 第一道门就 `HEAL skip=user_stopped` 直接返回。手动那条（覆盖安装 / 点通知）仍放行，否则装完新版反而起不来。

**② 「已停止」兜底通知不会被撤，服务回来后两条通知互相打脸**

`notifyBlocked` 发的是 1003 号通知，服务重新起来时只更新自己 1001 号，1003 那条「防烧屏守护已停止 · 点此恢复」会一直挂在通知栏里，用户看到的是「既停止了又在运行」。修法：`HealReceiver.cancelBlocked()`，服务 `startForeground` 成功后和自愈记账后各调一次。

**③ 隐身开关失败回滚写的是 `!hide`，不是真实旧值**

`setHideLauncherIcon` 失败时回写 `!hide`。这条只在「取反」调用时成立；一旦是幂等重放（传入值与已存值相同，比如程序里重复调用一次同步）且切换失败，就会把开关写反。修法：进函数先读 `old`，失败回滚 `old`。

**顺手核实的两条（和上一版报告有出入，纠正一下）**

- `ConfigProvider` **不是裸奔**：`call()` 先校验 token，再用 `Binder.getCallingUid()` 按包名白名单（本模块 / SystemUI / root / shell / 四个视频 App）二次校验，`query/insert/update/delete` 全返回空。lint 的 `ExportedContentProvider` 只是提醒「导出就要自己负责」，不是漏洞。
- 兼容性扫描没发现新的致命项：动态注册广播已带 `RECEIVER_NOT_EXPORTED`；FGS 声明了 `specialUse` + `PROPERTY_SPECIAL_USE_FGS_SUBTYPE`；没有 API 34 独有、却在 33 上必崩的调用；PendingIntent 全部 `FLAG_IMMUTABLE` 且 requestCode 不冲突（1002 / 1003 / 1004）；闹钟只有不精确 `setAndAllowWhileIdle`；磁贴 / 无障碍的 `exported` 与权限配对正确；`BOOT_COMPLETED` 拉 `specialUse` 不在 Android 15 的受限类型名单里。

**沙盒同步加了 7 条用例**（总 17 条）：停止后自动巡检不排闹钟、不记账、不判「刚自愈」；停止后手动恢复仍能拉起并重新排巡检；兜底通知能被撤干净；停止按钮 PendingIntent 指向 `ACTION_STOP`；以及原有 10 条。

**还没动的可疑点**（要动就得改行为，等你点头）：`ConfigProvider.call()` 在 hook 进程自己的 Binder 线程里做 `ConfStore.read()`（可能 fork su），极端情况下拖慢宿主；两处 `Thread.sleep` 在后台线程里做退避；`toLowerCase()` 未带 Locale；`R.array.xposed_scope` 已是死资源。
